## Как работал

Я проектировал архитектуру, принимал решения, формулировал требования.
AI реализовывал по моим спецификациям и проверял соответствие паттернам.

```
Я решаю: что строить и как (архитектура, паттерны, правила)
        │
        ▼
  Даю AI точный промпт с требованиями
        │
        ▼
  AI генерирует код
        │
        ▼
  Я проверяю: читаю код, запускаю линтер и тесты
        │
        ├── Нашёл проблему → даю уточняющий промпт → повтор
        │
        └── Всё устраивает → следующая задача
```

Итерации были быстрые. Архитектурные решения я принимал сам заранее, AI просто реализовывал.

## Этапы

### Этап 1 — Проектирование архитектуры

Я решил использовать **Clean Architecture + DDD + CQRS** с самого начала.
Логика простая: проект будет расти, нужна изоляция слоёв и тестируемость без БД.

Структура слоёв которую я выбрал:
```
domain/          ← бизнес-сущности, правила, интерфейсы репозиториев
application/     ← команды, запросы, хэндлеры, DTO
infrastructure/  ← SQLAlchemy, Redis, MinIO, JWT
interfaces/      ← FastAPI endpoints, dependencies
```

Правило которое я задал жёстко: **каждый слой импортирует только вниз**.
Domain не знает о FastAPI. Application не знает о PostgreSQL.

---

### Этап 2 — Реализация каркаса

Дал AI промпт со всеми требованиями по структуре.
После генерации прошёлся по каждому файлу и нашёл нарушения:

- `application/handlers/` напрямую импортировали `infrastructure/security/` и `infrastructure/storage/`
- Два endpoint'а делали `session.execute()` прямо внутри — обходя все слои
- Query handlers возвращали domain entities вместо DTO

Для каждой проблемы дал отдельный уточняющий промпт.

**Решение для infrastructure в application:**
Создал domain-интерфейсы `IPasswordService`, `ITokenService`, `IImageService`.
Хэндлеры теперь зависят от абстракций, не от реализаций. Dependency Inversion в действии.

**Решение для прямого SQL в endpoints:**
Создал полный стек для каждого случая: Query → Handler → Service → Repository.
Endpoint вызывает только Service.

---

### Этап 3 — Аудит архитектуры

После реализации попросил AI сделать полный аудит по правилам Clean Architecture.

Аудит выявил нарушения которые я пропустил при беглом просмотре:
- Мёртвый виджет с битыми импортами
- Несоответствие CQRS: часть command handlers возвращала entity вместо DTO
- Отсутствие `get_by_email` в абстрактном `UserRepository`

После каждой находки — отдельный промпт на исправление.

---

### Этап 4 — Тесты

Написал unit-тесты для всей бизнес-логики.
Принцип: тесты не должны требовать БД, Redis или MinIO — всё мокируется.
Это стало возможным именно потому что архитектура правильная: хэндлеры зависят от интерфейсов.

Покрытие по приоритету:
1. Auth handlers — самая критичная логика (логин, регистрация, роли)
2. Product handlers — CRUD + audit log
3. Review handlers — бизнес-правило "один отзыв на товар"
4. Domain entities — инварианты, методы

---

### Этап 5 — CI

Настроил GitHub Actions с двумя job'ами:
- `check` — ruff lint + format check + pytest с coverage
- `build` — docker build + verify import

Unit-тесты в CI не требуют внешних сервисов. Это осознанное архитектурное решение.

## Ключевые решения

### Clean Architecture вместо обычной структуры
При росте проекта `routers/`, `models/`, `schemas/` превращаются в хаос.
Clean Architecture даёт явные правила: где что лежит и откуда что импортировать.
Новый разработчик сразу понимает структуру.

### CQRS — разделение чтения и записи
Command изменяет состояние и ничего не возвращает (или возвращает только ID/DTO).
Query только читает и возвращает DTO.
Это упрощает тестирование и позволяет независимо оптимизировать чтение и запись.

### Domain interfaces для внешних зависимостей
Пароли, токены, хранилище изображений — всё за интерфейсами.
Можно поменять bcrypt на argon2, MinIO на S3 — application layer не трогаем.

### Cursor-based pagination
Offset ломается при вставке новых записей. Cursor стабилен.
Все списки в API используют `next_cursor`.

### pytest без БД
Правильная архитектура = тесты без инфраструктуры.
64 unit-теста запускаются за 0.5 секунды без поднятых сервисов.

## Проверки

### После каждого изменения
```bash
make lint         # ruff check
make format-check # ruff format --check
make test         # 64 unit-теста
```

### Архитектурный аудит (скриптом)
```python
# Проверка что application не импортирует infrastructure
for file in src/application/**/*.py:
    assert "from src.infrastructure" not in file

# Проверка что нет прямого session.execute в endpoints
for file in src/interfaces/**/*.py:
    assert "session.execute" not in file
```

## Что AI не делал

- Не выбирал архитектуру — я решил использовать Clean Architecture + DDD + CQRS
- Не проектировал доменную модель — сущности, их поля и связи определял я
- Не принимал решения по API — структуру эндпоинтов и контракты задавал я
- Не выбирал стек — FastAPI, SQLAlchemy, Redis, MinIO, Poetry были выбраны до начала

AI — инструмент реализации и верификации. Все архитектурные решения мои.
